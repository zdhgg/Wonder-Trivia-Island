# 导入核对页「不显示答案」问题报告与优化建议

- 日期：2026-09-28
- 范围：工具 → 导入（QuestionImportView / questionImport）
- 结论级别：**展示层缺陷**，非数据缺失

---

## 一、结论

不是题库里没有答案。**答案字段从 harness 提交到 API 返回，一路都在；只有导入核对页的表格没有渲染它。**

同时还有一个连带问题：即使现在给表格补一列「答案」，也只能看到 `A` 这一个字母——因为核对页拿到的数据里**不含选项文本和解析**。所以这不是「加一列」能解决的，需要同时补数据结构和展示形态。

---

## 二、证据链（逐层核对）

| # | 环节 | 位置 | 答案字段状态 |
|---|------|------|-------------|
| 1 | harness 提交 | `POST /api/questions/import/stage` | 完整（含 options / explanation） |
| 2 | 预检 | `backend/src/services/questionImport.js` `validateRawRow()` L500-536 | 仅保留 `answer` 字母，**丢弃 options 与 explanation** |
| 3 | 落盘 | `backend/data/staging/pending.json` | `rows[].answer` 存在；完整对象在 `validQuestions[]` |
| 4 | 读取 API | `getPendingImportBatch()` L1167-1179 | 只返回 `rows`，**有意不返回 `validQuestions`**（L1166 注释） |
| 5 | 页面渲染 | `frontend/src/views/QuestionImportView.vue` L166-174 | **表头只有 7 列，无「答案」列**；`row.answer` 收到但从未使用 |

实测 `backend/data/staging/pending.json` 第一行：

```json
"rows[0]": {
  "rowNumber": 2, "subject": "数学", "grade": "二年级", "semester": "上册",
  "knowledgeTag": "条件上手", "type": "乘法应用",
  "content": "题目要求填写乘法口诀。下面哪一个符合要求？",
  "imageUrl": "", "answer": "A", "difficulty": 1,
  "status": "valid", "issues": []
}
```

对照 `validQuestions[0]`，选项和解析都是齐的：

```json
"options": [
  { "key": "A", "text": "三六十八" },
  { "key": "B", "text": "3×6=18" },
  { "key": "C", "text": "18÷3=6" },
  { "key": "D", "text": "3+6=9" }
],
"answer": "A",
"explanation": "题目要的是乘法口诀，口诀用汉字写成一句，所以选「三六十八」。…"
```

**旁证**：题库查看页 `frontend/src/views/QuestionCatalogView.vue` L674-700 已经完整展示「答案 + 选项高亮 + 解析 + 难度 + 知识点」。展示能力是现成的，只是核对页没用上。

---

## 三、根因

`previewQuestionImport()` 的输出结构被「预检」和「审核」两个场景复用了。

`validateRawRow()` 构造的 `preview` 对象为了轻量，只挑了标量字段（subject / grade / semester / content / answer / difficulty）。审核页需要的选项与解析是嵌套结构，被排除在外；而 `getPendingImportBatch()` 又刻意不把 `validQuestions` 暴露给页面，理由是「页面只负责展示」。

两者叠加的结果，就是审核页拿不到可核对的答案上下文。

---

## 四、优化建议

### P0 — 必须做（否则核对等于走过场）

**1. 给 `preview` 补上 options 与 explanation**

改 `backend/src/services/questionImport.js` 的 `validateRawRow()` 返回结构：

```js
preview: {
  rowNumber,
  subject,
  grade,
  semester,
  knowledgeTag,
  type,
  content,
  imageUrl,
  options: OPTION_KEYS.map((optionKey, index) => ({
    key: optionKey,
    text: optionTexts[index]
  })),
  answer,
  explanation,
  difficulty: Number.isNaN(difficulty) ? "" : difficulty
}
```

注意：校验失败的行 `optionTexts` 可能是空串，前端要按空值兜底，别渲染出 `undefined`。

**2. 核对页改为「紧凑行 + 可展开详情」**

不建议简单加一列「答案」——因为只显示字母没有核对价值。推荐：

- 折叠态：`行号 · 学科/年级/学期 · 题干 · 状态`（贴近现状，信息密度高）
- 展开态：4 个选项（正确答案高亮）+ 解析 + 题型 + 知识点 + 难度 + 配图缩略图

这样既保住了一屏看多行的效率，又能真正逐题核对。实现上给 `previewRowsToShow` 加一个 `Set` 记录展开的行号即可，无需改接口。

**3. 同步修正表头列宽**

`QuestionImportView.vue` L827 的 `grid-template-columns` 与实际列数强耦合。若仍要加「答案」列，必须同步改这里，否则列会错位。

### P1 — 强烈建议

**4. 解除 12 行预览上限**

`useQuestionImportReview.js` L10 `PREVIEW_ROW_LIMIT = 12`，配合 L231 的「仅展示前 12 行」提示，意味着 2000+ 题的批次实际只看了 12 行。建议改为：

- 分页或「加载更多」（每页 20）。
- 配合筛选：只看警告 / 只看错误 / 按学科分组。

**5. 表头吸顶**

`.preview-table__head` 加 `position: sticky; top: 0; z-index: 1;`，长表格滚动时保留列语义。

### P2 — 质量提升

**6. 抽样核对策略**

与其固定看前 12 行，不如整批随机抽 N 道展示完整信息。前 12 行往往是同一批集中生成的同质题，代表性差。

**7. 答案自洽性告警（仅 warning，不阻断）**

系统目前只校验 `answer ∈ {A,B,C,D}`，不校验语义。可加：

- 选项文本两两重复检测；
- 正确答案的文字是否在解析里被提及；
- 干扰项是否与正确答案过于接近（如同时出现 `3×6=18` 与 `6×3=18`）。

这类检查能抓住 harness 生成的主要错误类型，成本却很低。

**8. 配图题可见性**

`imageUrl` 已进入 preview 但核对页完全没体现。带图题在当前页面上无法判断对错，建议至少标记「含配图」并给缩略图。

**9. 多题型扩展**

当前链路硬编码 `OPTION_KEYS = ["A","B","C","D"]`，`answer` 与选项数量都强绑四选一。若后续要支持判断、填空、连线题，preview 结构需要预留题型维度。

---

## 五、附带发现

- 截图中文案「仅展示前 12 行，完整校验已覆盖全部数据」有误导性。「完整校验」指格式校验，不指人工核对，容易被理解成「已经看过了」。建议改成明确的风险提示，例如「仅展示前 12 行，剩余行未经人工核对」。
- 落盘数据里的 `knowledgeTag` 是「条件上手」这类表达，语义偏模糊。核对页若能高亮空白或异常标签，有助于发现 harness 生成质量问题。
- 值得肯定的一点：`answer` 做了 `.toUpperCase()`，`subject` / `grade` / `semester` 都有别名映射，容错设计是到位的。

---

## 六、建议实施顺序

1. 先改 `validateRawRow()` 的 preview 结构（后端，一处改动，风险低）。
2. 再做核对页的答案列 + 行展开（前端，一次交付完整体验）。
3. 最后处理 12 行上限与筛选（前端）。

前两步完成后，核对页才算真正具备「人对答案负责」的能力。
